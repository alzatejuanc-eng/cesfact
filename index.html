1.2 Los tres canales de integración con Cessio.Net

CRÍTICO para el desarrollo: El Canal 2 (SQL directo) solo es posible porque Cessio.Net usa PostgreSQL. La latencia analítica es 1000× menor que vía API. Usarlo para todos los dashboards, KPIs y scoring IA. Usar el Canal 1 (API) solo para operaciones transaccionales (lectura puntual + escritura).

Propósito: Operaciones transaccionales. Lee datos puntuales de operaciones, facturas, clientes. Escribe gestiones, promesas, estados, descuentos aprobados.

2.2 Autenticación JWT — flujo completo

Flujo de autenticación
1

POST /api/auth/login { email, password }

Backend valida contra hash bcrypt en tabla usuarios. Si válido: genera access token (15 min) + refresh token (24h) con JTI único. Guarda JTI en Redis. Devuelve ambos tokens.

2

Frontend: almacenar tokens en memoria (no localStorage)

Access token en variable de estado React. Refresh token en httpOnly cookie. NUNCA en localStorage — viola LOPDP si hay XSS.

3

Cada request: Authorization: Bearer {access_token}

Backend valida firma JWT. Si válido: extrae user_id y role del payload. Verifica RBAC según el endpoint. Sin consulta a BD en cada request.

4

Access token vencido: POST /api/auth/refresh

Frontend envía refresh token automáticamente (interceptor Axios). Backend verifica JTI en Redis. Si válido: emite nuevo access token. Si no: sesión terminada, redirigir a login.

5

Al desactivar usuario: invalidar sesión inmediatamente

Administrador desactiva usuario → backend elimina todos los JTI de ese usuario en Redis → próxima llamada con refresh token falla → usuario queda fuera en segundos, sin esperar expiración natural.

Algoritmo de clasificación

Función classify_operation(operacion_id)
1.Obtener la fecha de vencimiento más antigua entre todas las facturas de la operación (regla de múltiples facturas — ver 4.3)
2.Calcular dias_vencidos = MAX(0, CURRENT_DATE - fecha_vencimiento_mas_antigua)
3.Si dias_vencidos == 0 AND CURRENT_DATE >= fecha_vencimiento - 8 → tramo = Preventiva
4.Si dias_vencidos > 0 → aplicar rangos de la tabla anterior para asignar tramo
5.Calcular prioridad interna (ver 4.2)
6.Si tramo cambió a Avanzada (61d) y no existe escalamiento automático activo: crear registro en escalamientos con tipo=automatico_tramo
7.Persistir resultado en clasificacion_operaciones (upsert por operacion_id)

4.3 Regla de múltiples facturas por operación

Regla crítica: Una operación de factoring puede tener múltiples facturas con distintas fechas de vencimiento. El tramo de la operación se calcula usando la factura con mayor antigüedad (más días vencidos). Si la factura más antigua tiene 45 días, la operación clasifica en Media — aunque las otras facturas sean recientes.

Implementación: en la query de clasificación, siempre usar MIN(f.fecha_vencimiento) para obtener la fecha de vencimiento más temprana del grupo de facturas de la operación.

5.2 Regla anti-hostigamiento — implementación técnica

Máximo 1 contacto por cliente por día. Se verifica ANTES de permitir el registro. Si el cliente ya fue contactado hoy, el formulario muestra el aviso y bloquea el envío. La excepción es el tipo 'observacion' que NO cuenta como contacto.

Verificación de anti-hostigamiento

Query de verificación (ejecutar al abrir el formulario y al momento de guardar):

Contar gestiones del día actual (DATE(created_at) = CURRENT_DATE) para ese cliente_id donde tipo != 'observacion'. Si COUNT >= 1: bloquear y mostrar mensaje.

  • Una operación vencida con 2 facturas del mismo cliente → cuenta como 1 contacto al cliente, no 2
  • El Supervisor puede también contactar al cliente → también consume el cupo diario
  • El sistema automático (WhatsApp preventivo D-8) también consume el cupo si aplica
  • Las notificaciones automáticas de promesa incumplida SON contacto — verificar cupo antes de enviar

7. Módulo 5 — Motor Financiero

7.1 Los 3 tipos de liquidación — fórmulas y validaciones

Liquidación Ordinaria

Cuándo: Pago en fecha de vencimiento o dentro del plazo pactado.

Fórmula:
descuento = monto_factura × (tasa / 100)
iva = descuento × 0.15
total = descuento + iva

Sin cargos adicionales. Sin GAO. Tasa y monto desde Cessio.Net vía API.

Liquidación Anticipada

Cuándo: El cliente paga antes de la fecha de vencimiento pactada.

Fórmula:
descuento = monto × (tasa/100) × (dias_reales / dias_contratados)
iva = descuento × 0.15
total = descuento + iva

dias_reales = días desde desembolso hasta pago. dias_contratados = días originales del contrato.

Liquidación Vencida

Cuándo: Pago posterior a la fecha de vencimiento.

Fórmula:
descuento = monto_factura × (tasa/100)
periodos = CEILING(dias_vencidos / 10)
gao_adicional = 0.008 × monto_factura × periodos
iva_gao = gao_adicional × 0.15
total = descuento + gao_adicional + iva_gao
— nota_descuento (si aprobada por GG)

7.2 Notas de descuento — flujo con aprobación GG

1

Asistente calcula la liquidación vencida en el motor

Ve el total con GAO. Puede hacer clic en "Solicitar nota de descuento" e ingresar el % propuesto.

2

Se crea registro en aprobaciones tipo=nota_descuento estado=pendiente

El payload incluye toda la liquidación calculada: descuento base, GAO, IVA, % nota propuesto, monto nota, total con nota. Gerencia ve todos estos datos al aprobar.

3

Gerencia aprueba, modifica % o niega desde su bandeja

Si aprueba: aprobaciones.estado = aprobado, firma digital registrada. Si modifica %: registra el % aprobado real. Si niega: Asistente liquida sin descuento.

4

Motor aplica el descuento y dispara flujo Contifico

El total final incluye el descuento aprobado. El POST a Contifico incluye el ID de aprobación como referencia auditora.

7.3 Orden de aplicación de abonos (pagos parciales)

Regla invariable: Los costos siempre se pagan ANTES que el capital. Nunca se reduce el capital si hay costos pendientes.

Orden de aplicación: 1° GAO adicional → 2° IVA del GAO → 3° Descuento contractual (comisión) → 4° IVA del descuento → 5° Capital pendiente

12.1 Scoring de comportamiento de pago

Cuándo recalcular: Al registrar un pago (webhook), al registrar una promesa incumplida (job nocturno), al crear/cerrar una operación nueva. El resultado se guarda en tabla scoring_clientes y se lee desde el dashboard y el formulario de gestión.

Query de scoring (Canal 2 — PostgreSQL directo)

La query calcula el score 0-100 por cliente usando los últimos 24 meses de historial:

  • dias_retraso_prom: promedio de días de retraso en pagos históricos (AVG de fecha_pago - fecha_vencimiento)
  • pct_pagos_puntuales: % de pagos realizados en la fecha pactada o antes
  • promesas_rotas_12m: COUNT de promesas con cumplida=FALSE en los últimos 12 meses
  • otras_ops_vencidas: COUNT de otras operaciones actualmente vencidas del mismo cliente

Fórmula del score: GREATEST(0, LEAST(100, 100 - dias_retraso_prom * 2.0 - promesas_rotas_12m * 10.0 + pct_pagos_puntuales * 1.5))

14. Acceso PostgreSQL Directo — Queries Analíticas (Canal 2)

14.1 Query de madurez de cartera (Informe Directorio + Dashboard Gerencia)

Usa window function SUM OVER() para calcular el % de cada tramo sobre el total en una sola query. Esta query es imposible de replicar eficientemente vía API. Tiempo estimado de ejecución: 8-15ms.

QUERY_MADUREZ_CARTERA

SELECT: tramo (calculado con CASE WHEN sobre días vencidos), COUNT de operaciones, SUM de saldo_pendiente, ROUND(SUM(saldo) × 100.0 / SUM(SUM(saldo)) OVER (), 2) AS pct_cartera

FROM: operaciones JOIN (subquery facturas: saldo_pendiente = SUM(monto - pagado) WHERE estado != 'pagada')

WHERE: operaciones.estado NOT IN ('pagada', 'anulada')

GROUP BY: tramo | ORDER BY: MIN(CURRENT_DATE - fecha_vencimiento)

15.2 Opciones de implementación (decidir en Fase 1)

Opción A — HTTP Webhook

Latencia: <1 segundo

Cessio.Net necesita: Sistema de webhook HTTP saliente (POST a URL configurable)

Verificación de autenticidad: HMAC-SHA256 en header X-Cessio-Signature

Si la plataforma está caída: El webhook puede perderse. Cessio.Net debe reintentar o la plataforma debe implementar polling de recuperación.

Recomendación: Opción primaria si Cessio.Net la soporta

Opción B — PG LISTEN/NOTIFY

Latencia: <100ms

Cessio.Net necesita: Trigger en tablas clave que ejecute NOTIFY

Plataforma necesita: Proceso persistente con asyncpg escuchando el canal. Si se cae: reconectar y revisar lo que se perdió.

Ventaja: El NOTIFY ocurre dentro del commit. Garantía de entrega si la plataforma está conectada.

Recomendación: Mejor opción técnica si se puede añadir triggers en Cessio.Net

Opción C — Polling periódico

Latencia: 2-5 minutos

Cessio.Net necesita: Solo GET /operaciones?modified_since={timestamp} (API estándar)

Implementación: Celery beat o Cloud Scheduler ejecuta el job cada 2-5 minutos

Ventaja: Nunca pierde eventos. No requiere modificar Cessio.Net.

Desventaja: Lag de 2-5 min en el flujo Contifico. Aceptable para la mayoría de casos.

Recomendación: Fallback siempre disponible

15.3 Verificación HMAC-SHA256 (Opción A)

Implementar en el receptor de webhooks. Antes de procesar cualquier payload:

1. Extraer firma del header: X-Cessio-Signature: sha256={hash_hex}

2. Calcular HMAC del body raw con el secreto compartido: hmac.new(secret.encode(), body_bytes, hashlib.sha256).hexdigest()

3. Comparar usando hmac.compare_digest() (evita timing attacks)

4. Si no coincide: responder 401 y registrar en log. Si coincide: responder 200 inmediatamente y procesar en background.

Responder 200 ANTES de procesar. Si la plataforma tarda en responder, Cessio.Net puede hacer un retry. Siempre: aceptar primero, procesar en background.
